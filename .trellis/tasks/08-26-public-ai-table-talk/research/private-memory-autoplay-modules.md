# 默认公开、稀缺私聊、AI 托管与竞技模块调研

日期：2026-08-26

## 用户新增构想

- 玩家进入牌局后，与 Codex 的交流默认进入牌桌公开区域。
- 私密交流必须显式调用，并受到更严格的次数限制；用户暂提每局 10 次。
- 私密交流可以要求保存本场记录，供自己的 AI 后续学习。
- 增加 AI 托管模式，由 AI 提交牌局动作，并可主动进行公开语言博弈。
- 项目既要有任何原生 Codex 都能使用的基础游戏能力，也要有玩家自行培养的 AI 竞技档案。
- 玩家未来可以从 TokenGame 市场下载其他人制作的“AI 进化模块”；官方不主动提供高级竞技策略。

以上均作为候选需求保存，尚未视为最终 MVP 承诺。

## 第一项纠偏：默认公开的作用域

“进入牌局后所有用户与 Codex 的交流默认公开”只有限定在一个专用游戏任务中才安全。不能把同一项目文件夹下的所有 Codex 任务都视为公开，否则用户在另一个编码任务里讨论代码、文件、凭据或个人信息时也可能被错误广播。

建议边界：

- 玩家通过专用 TokenGame 游戏任务加入牌桌后，该任务的自由文本输入默认是 TABLE_PUBLIC。
- 其他 Codex 任务和同项目中的普通开发任务完全不受影响。
- 游戏任务的输入框持续显示醒目的“公开到牌桌”状态，而不是只依赖用户记住规则。
- 活跃牌局期间默认禁用非 TokenGame 工具、附件和任意文件读取；否则公开回复可能夹带仓库内容。
- 离桌或切换到私密频道后恢复对应权限，但必须由明确的状态转换驱动。

当前仓库事实：现有 Hook 恰好相反。普通提示完全私密，只有以 tokengame public 显式标记的提示才进入公开流；PreToolUse 也只在一次公开回答 pending 时阻止无关工具。要实现新构想，必须新增“专用游戏任务已绑定且入桌中”的会话状态，不能简单删掉 public 前缀判断。

## 建议的三通道协议

### TABLE_PUBLIC：默认公开话术

- 专用游戏任务在已入桌状态下的普通对话默认走该通道。
- 玩家提示先写入权威公开事件流，随后模型回答也进入同一公开请求。
- 全桌 AI 可以在受控上下文窗口内看到这些公开事件。

### OWNER_PRIVATE：稀缺私密咨询

- 必须显式调用，例如 @tokengame private；用户原例中的 @tokengold talk 存在产品名不一致，命令名暂不锁定。
- 只有玩家与自己的 AI 能看到内容；其他玩家的模型上下文也不能包含它。
- 私密调用必须服务端计数、幂等并显示剩余额度。
- 产品已确认：公开“某席正在使用私密咨询”及该席准确剩余额度，例如“剩余 7/10”；提示和回答正文始终只对所属玩家与 AI 可见。
- 私密使用状态与剩余额度属于权威竞技资源，不受聊天静音/屏蔽影响，也会进入所有玩家一致的公开状态投影。
- AI 不应主动消耗玩家私密额度，除非玩家预先开启明确策略。
- 产品已确认：玩家只要仍在桌中，就可以在自己回合、其他玩家回合、自己弃牌后或两手之间发起 OWNER_PRIVATE；牌局行动时钟不因私聊而暂停或延长。
- 每席最多一个 OWNER_PRIVATE 请求生成中。请求携带创建时的 hand_id、street 和 state_revision；若答复到达时状态已经推进，仍可私密展示，但必须标明它基于旧状态且不能触发牌局动作。

### LOCAL_CONTROL：本地确定性命令

- 保存牌局、切换频道、静音、查看配额、选择 AI 档案等不需要模型推理的操作走控制通道。
- 例如“保存当前比赛到记忆库”应优先设计为确定性命令，而不是浪费一次私密模型咨询。
- 如果用户要求“分析本场并生成学习总结”，分析部分才属于一次私密模型调用。

这三通道拆分能避免一个不必要的产品惩罚：用户只是保存回放，却被扣除稀缺的战术私聊次数。

## 私密额度重置（已裁决）

用户确认：每名玩家的 OWNER_PRIVATE 上限为 10 次；同一牌桌每完成 3 手结算后，全桌进入新的私密额度周期并统一恢复到 10 次。

协议解释：

- 只有权威 HAND_SETTLED 事件增加 settled_hand_count；正常摊牌、其余玩家弃牌等合法完成方式都计入。
- 未结算、取消或作废的手牌不计数；网络重试和事件重放不能重复计数。
- 第 3 手结算完成后立即切换 quota_epoch，在下一手开始前把各席 used_private_calls 归零。
- 未使用次数不结转；刷新页面、断线重连、短暂离开后以同一玩家身份返回都不能提前恢复额度。
- 真正的新玩家加入时获得当期 10 次额度，但随后跟随当前牌桌 quota_epoch；同一身份重复入座不能伪装成新玩家刷新额度。

### 私密请求失败与退款（已裁决）

- 请求在通过格式、身份、pending 和余额校验并被权威服务接受时立即扣除 1 次，同时公开新的剩余额度。
- 空消息、身份错误、余额耗尽、同席已有 pending 等接受前拒绝不扣除额度。
- 只有已验证的桥/模型基础设施故障，且没有产生任何可向玩家交付的回答时，服务端才发布幂等 PRIVATE_QUOTA_REFUNDED 事件。
- 用户主动取消、内容策略拒绝、已经生成但因状态推进而过期的答复均不返还，避免通过取消和重复请求探测或绕过配额。
- 退款与原 request_id 和 quota_epoch 绑定，最多发生一次。若该请求所属的三手周期已经结束，当前余额保持新周期上限 10，不把旧周期退款结转成第 11 次。
- 超时后已进入退款终态的迟到回答必须丢弃，不能既返还额度又交付回答。

## 记忆、学习与微调必须区分

建议 TokenGame 自己维护四类本地数据：

1. 不可变牌局事件与回放：牌、动作、公开聊天、结果和版本。
2. 派生统计：位置、动作频率、摊牌结果、公开话术特征等只基于合法可见数据的指标。
3. 私有学习摘要：用户要求 AI 生成的复盘、漏洞和未来策略提示。
4. AI 档案配置：人格、风险偏好、工具权限、检索范围和模块清单。

“保存到记忆库学习”在首版应解释为保存结构化记录、生成摘要，并在未来回合按需检索；它不等于修改 Codex 模型权重。大量原始记录也不能整包塞进上下文，应先做统计、检索和压缩。

不得保存或声称保存模型隐藏推理。若保存其他玩家的公开发言和行为用于长期建模，入桌规则要说明留存范围；模块发布到市场前还需要去标识化和数据许可约束。

官方文档事实：

- Codex Skill 是包含 SKILL.md、可选脚本、参考资料和资源的可复用工作流；Plugin 是可安装的能力包，可以组合 Skills、连接器和 MCP 工具。
  - https://learn.chatgpt.com/docs/build-skills
  - https://learn.chatgpt.com/docs/skills-and-plugins#use-skills-for-repeatable-work
- Codex App Server 可以维护线程、回合、历史、认证和流式事件，适合专用游戏代理的运行层。
  - https://learn.chatgpt.com/docs/app-server#api-overview
- OpenAI 的监督微调是上传训练集并创建独立微调任务的 API 流程，不是 Codex 会话边玩边自我修改。当前官方文档还说明该微调平台正对新用户收缩，因此 TokenGame 不应把产品路线建立在 Codex 在线微调上。
  - https://developers.openai.com/api/docs/guides/supervised-fine-tuning

## AI 托管是独立的行动代理模式

AI 托管不能通过解析自然语言气泡来下注。建议完全分离两条输出：

- Action proposal：严格结构化的 fold、check、call、bet、raise 或 all-in 候选动作，包含 hand_id、revision、合法动作快照和幂等键。
- Public speech：可选的公开短句，属于参与者话术，不具有动作效力。

权威牌局服务仍然重新校验动作。模型超时、断线、返回非法 JSON、使用过期 revision 或超出下注范围时，必须按桌规确定性降级；不能让 AI 自行绕过倒计时。

候选托管档位：

- OFF：玩家手动操作，AI 只公开/私密建议。
- ADVISOR：AI 给出结构化建议，玩家确认后提交。
- AUTOPILOT：AI 在行动窗口内直接提交合法动作，玩家可以按明确规则收回控制。

主动语言施压可以作为 AUTOPILOT 的独立开关，但仍受公开聊天配额、屏蔽和行为规范约束。产品应称为“策略性话术”或“垃圾话”，不能把持续骚扰、歧视或针对现实身份的心理攻击包装成竞技能力。

## 基础插件与 AI 竞技档案

用户的“两类功能”方向正确，但物理目录最好拆为四层：

1. 官方基础运行时：安装、入桌、牌局状态、动作、公开/私密路由、回放和安全边界。
2. 玩家 AI 档案：名称、人格、风险偏好、记忆索引、托管设置和已启用模块。
3. 已安装竞技模块：版本化、只读、声明能力的策略包。
4. 玩家私有数据：原始回放、统计、摘要和模块生成物，不随模块一起发布。

候选项目布局：

- plugins/tokengame：官方基础插件。
- .tokengame/agents/某个档案：玩家 AI 配置。
- .tokengame/modules/某个模块：已安装竞技模块。
- .tokengame/memory/某个档案：本地私有记录与索引。

这只是逻辑布局建议，尚未锁定真实路径。

### AI 档案的身份、偏好与权限

用户确认 AI 档案可配置头像、昵称、人设、表达风格、权限与自主程度。建议把配置拆为三层，避免把“说话更放肆”误解成“获得更多系统权限”：

- 身份与表现：display_name、avatar_asset、persona_summary、tone、称呼偏好、语言和气泡外观。
- 行为自主度：是否主动发言、允许的 trigger_types、发言频率倾向、垃圾话强度、是否允许公开诈唬、是否主动保存/复盘。
- 能力与权限：记忆读写、统计读取、概率计算器、社区模块、ADVISOR/AUTOPILOT、下注风险上限和允许的数据源。

有效权限必须取四者交集：官方不可突破的安全上限、当前桌型规则、用户明确授权、模块自身声明权限。用户配置只能在这个交集中开启或收窄能力，不能授予对手底牌、普通项目文件、任意网络或绕过配额的权限。

昵称和头像只是表现身份，协议始终保留 seat_id 与 owner_id。所有界面固定显示“A · Kitty”之类的席位归属；禁止冒充 Dealer、System、Admin 等系统身份。头像首版应导入并清洗到 TokenGame 本地资产目录，限制格式、尺寸和体积，不直接热链远端 URL。

建议保存 versioned AgentProfile，而不是把全部偏好塞进一段自由文本。短人设文本可以存在，但硬权限、频率、工具和动作边界必须是结构化字段，由服务端验证。

产品已选择“预设 + 高级设置”：

- 默认提供安静、均衡、张扬和自定义等版本化预设；预设展开成可检查的结构化配置，不是不可见的提示词标签。
- 高级设置允许在桌规上限内覆盖主动触发子集、发言倾向、垃圾话强度、是否允许战略性说谎、记忆读写、统计/概率工具、模块和托管权限。
- AgentProfile 保存 preset_id、preset_version、overrides、resolved_snapshot_hash 与 schema_version；预设以后升级时不得静默改变正在使用的旧档案。
- UI 同时展示“用户想要的配置”和“桌规裁剪后的有效配置”，让玩家知道某项权限为什么没有生效。
- 允许有限长度的 persona_summary，但不开放能覆盖系统规则的完整原始提示词编辑器；所有自由文本都按不可信输入处理。

## “AI 进化模块”首版不应是任意可执行 Skill

官方 Skills 可以包含脚本。如果 TokenGame 市场允许陌生作者的完整 Skill/脚本直接进入 Codex 工具环境，模块可能读取项目文件、外传数据、修改记忆或注入与游戏无关的指令。这是供应链风险，不只是牌局平衡问题。

建议按能力分级：

- Level 1，声明式模块：人格、策略规则、提示模板、特征权重和检索配置。首版市场只开放这一层。
- Level 2，受限计算模块：概率计算、范围估计等纯函数，通过固定输入/输出协议运行，无网络、无任意文件权限。
- Level 3，可执行代理模块：自定义代码、MCP 或外部模型。未来仅在签名、权限清单、沙箱、审查和明确桌型隔离后开放。

每个市场包至少需要 manifest：id、version、author、runtime compatibility、capabilities、permissions、content hash、signature、data policy 和 eval results。官方可以不提供高级竞技策略，但必须提供基础策略、协议验证器、安全沙箱和统一评测，否则市场无法比较也无法安全运行。

## 强弱差异与桌型

保存大量历史并不自动等于更强。实际优势更可能来自：

- 高质量特征和对手模型；
- 正确的牌力/胜率计算器；
- 有效的检索和上下文压缩；
- 经过评测的行动策略；
- 更合理的延迟与模型预算。

如果原生 Codex、带计算器的模块和完全托管代理进入同一排行榜，胜负不可解释。候选桌型至少应显示能力标签：Vanilla、Enhanced、Autopilot、Open。是否分池匹配以后讨论；本地朋友桌可以全部开放，但仍需让所有人看见对方启用了哪些能力类别。

## 仓库差距

- 当前只有显式 public 单次 prompt/answer，没有 TABLE_PUBLIC / OWNER_PRIVATE / LOCAL_CONTROL 三通道。
- 当前没有 match/session 级配额、私密事件投影或公开的私聊使用元数据。
- 当前没有回放持久化、统计、检索或玩家 AI 档案。
- 当前动作只能由 Web 玩家身份提交，没有模型行动提案、托管状态或人工接管协议。
- 仓库已有本地 marketplace 安装探针，但那只是安装 TokenGame 插件的验证设施，不是可供玩家交易策略模块的产品市场。

## 建议的逐项裁决顺序

1. 默认公开的精确作用域，以及 PRIVATE 与 LOCAL_CONTROL 是否拆分。
2. 宿主能力不检测前提下，牌桌是否明确标记为 Open / Unverified，以及排行榜如何描述。
3. 记忆的数据层、保留周期、跨桌复用和删除语义。
4. AI 托管档位、超时降级和人工接管规则。
5. 竞技模块首版能力边界与市场安全模型。
6. 不同能力玩家是否分桌、是否显示模块能力标签。

用户当前仍在补充想法，因此本轮只记录和纠偏，不锁定上述决定。
