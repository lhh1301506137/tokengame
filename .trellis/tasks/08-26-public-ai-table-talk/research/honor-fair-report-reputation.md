# 公平场尽力检测、举报与信用体系调研

日期：2026-08-26

## 产品前提

用户先提出依靠自律声明，随后明确修正：公平场必须由 TokenGame 尽力检测模型和推理强度，用来筛掉一批想临时使用高级模型“炸鱼”的玩家，但产品不得保证检测绝对可靠。两类牌桌为：

- 开放能力桌：允许任意宿主配置和合规竞技模块。
- 公平场（尽力检测、不保证）：目标是让使用同模型、同推理强度的玩家进入；自律确认之外叠加 Codex App Server 结构化信号检测，并考虑举报和信用体系。

## 必须纠正的命名与能力边界

TokenGame 现在需要读取其实际使用的 App Server 结构化信号并生成 detection receipt，而不是只接受勾选声明。但本机协调器、App Server 和自定义 provider 都由玩家控制，检测仍不是可信执行环境或上游模型证明。因此 UI 可使用“公平场”，但必须在同一视觉层级持续附带“TokenGame 尽力检测 · 不保证”，不能使用无修饰的“已验证同模型”。

这里的公平是“基础模型资源分档”，不是“成品 AI 能力相同”：为无法长期使用顶尖模型的玩家提供一个约定相同基础模型与推理强度的竞技分组，同时保留玩家训练、配置和养成 AI 的差异。它更接近同一重量级或同一基础引擎下比赛。

只要求模型和推理强度相同仍不足以形成相近能力。以下差异可能比模型差异更大，但已被明确选择为合法的竞技变量：

- 是否加载概率/范围计算器；
- 是否读取长期牌局记忆和对手统计；
- 是否启用社区策略模块；
- 是否允许 ADVISOR / AUTOPILOT；
- 上下文长度、压缩和检索质量；
- 人设、策略偏好和主动发言配置；
- 自定义 provider 对模型名称或强度的解释差异。

因此，公平场不要求各席的 memory、opponent_stats、equity_calculator、community_modules、advisor 或 autopilot 配置相同。`table_capability_manifest` 仍可声明全桌共同的安全上限和允许能力，但不负责把各席能力抹平。

用户选择不向对手公开各席的能力类别。能力开关、模块清单、版本、数量、记忆状态、工具与托管配置都属于竞技秘密；对手只能从公开话术和动作中自行推测。入桌公告必须明确“能力可能不同且不会公开”，否则隐藏会被误解为能力不存在或完全相同。

隐藏仅作用于对手投影和公共产物，不影响所属玩家查看自己的有效配置，也不妨碍权威组件为权限执行、安全验证与私有审计持有必要元数据。实现时要特别防止模块名、工具调用轨迹、内部错误码和调试日志通过公共事件或失败提示旁路泄露。AI 在线/离线、思考中、公开输出、牌局动作和已确定公开的私聊使用状态仍是比赛事实，不属于能力清单披露。

TokenGame 能公平执行的只有自身权威控制的规则与资源，例如行动时钟、公开/私密聊天额度、触发次数和服务端动作校验。Codex 账户额度、宿主限速、上下文质量、中转稳定性和玩家是否诚实申报均不受 TokenGame 控制，必须在公告中明确排除，不能借“照顾资源有限用户”之名承诺不存在的完全成本公平。

## 建议的两种桌型

### OPEN_CAPABILITY

- 允许任何能正常驱动专用 Codex 游戏线程的宿主模型/provider。
- 允许桌规列出的社区模块、记忆、工具与托管能力。
- 不展示可信模型身份，不声称能力同级。
- 排行榜只描述实际牌局结果和桌型，不解释为模型能力排名。

### HONOR_MATCHED（UI：公平场 · 检测不保证）

- 房主或标准池发布目标 model_label、effort_label；TokenGame 先校验目标目录，再通过 App Server 的 config/thread/turn 结构化信号做尽力检测。
- 玩家入桌前确认：“我的宿主模型和推理强度符合目标；我理解 TokenGame 会检测但不能保证；各席的记忆、工具、模块和 AI 养成水平可能不同；绕过检测可能被举报。”
- 各席允许在桌规安全上限内使用不同的 AgentProfile、历史记忆、对手统计、概率工具、社区模块和托管配置；这些差异是竞技内容，不构成违反同模型声明。
- 上述能力配置不向对手展示；公共 HUD、事件、回放和排行榜均不包含能力徽章、模块清单或配置摘要。
- TokenGame 对所有席位执行相同的牌局规则、行动时钟和桌内调用/聊天配额，但不保证各自 Codex 账户的额度、延迟或 provider 服务质量相同。
- 未确认不能入桌；确认记录包含 ruleset_hash、player_id、timestamp 和公告版本。
- 桌面始终显示“公平场 · 检测不保证”和每席当前检测状态，不能只在一次性弹窗中隐藏风险，也不能显示“已验证同模型”或“AI 能力相同”等误导性文案。

## 匹配入口

用户选择同时提供公共标准匹配池和私人自定义房间：

- 公共标准匹配池：TokenGame 维护版本化 model/effort 目标目录，玩家选择并确认目标后通过结构化预检，再按该组合与其他权威桌规键精确分池。目录规范标签，检测筛选普通错配；两者都不构成真实上游模型证明。
- 私人自定义房间：房主填写目标 model/effort 展示文本，通过未公开邀请入口组桌。它不进入公共标准池、不获得平台标准配置标识，自定义文本必须经过长度、字符和系统冒充校验。
- 玩家可在本地保存上次选择，但每个新桌以及目标或 ruleset_hash 变化后仍需重新确认和重新检测。实际 provider 与上游模型仍可能被本机或中转重写，不能因预检通过就声称已证明。
- 标准目标目录必须版本化。条目停用只影响新队列，不能追溯改写排队快照、已开始牌桌、确认记录或历史回放。
- 公共池采用版本化 capability ceiling：低 capability_class 玩家可在自选范围内进入更高 ceiling，高 capability_class 玩家不能进入更低 ceiling。超时只能按预设向上扩展匹配票据；不可比较的模型组合不自动排序。

该双入口兼顾公共匹配的一致命名与长尾模型/朋友局的灵活性，但会增加目录治理、队列密度和空池处理问题。人数不足时是否允许跨目标建议或扩池必须另行确定，不能静默破坏同模型承诺。

## 举报体系的证据层级

举报类型必须分开：

1. 可直接从 TokenGame 协议事件核实：刷屏、公开聊天内容、频率超限、非法动作请求、故意断线/超时模式、利用协议漏洞，以及本局结构化检测出现的错配/缺失/过期状态。
2. 需要人工结合记录判断：合谋、筹码转移、骚扰语境、多账号嫌疑。
3. 当前无法技术证明：结构化信号背后的真实上游模型/provider 是否如实执行、玩家是否修改本机检测链、是否在外部使用未披露 AI。

第三类只能记作 allegation，不能因单次或多数举报自动判定作弊。玩家“太强”“风格不像目标模型”都不是可靠证据。

举报应自动附带 table_id、hand_ids、event seq 范围、ruleset_hash、双方身份、时间和相关公开聊天；举报人只补充类别与说明。PokerStars 也要求报告提供用户名、手牌/牌桌标识和可疑聊天，并由完整性团队复核，而不是由举报本身直接定罪。

## 信用体系不应是一个可被刷票的总分

建议把信用拆为不同维度：

- reliability：完成牌局、断线、恶意拖时等权威可观测行为。
- conduct：经复核成立的骚扰、刷屏或违规事件。
- honor_history：参加多少场自律桌、作出多少次声明、是否有已复核成立的虚假声明。没有成立记录不等于证明诚实。
- community_feedback：赛后评价，仅作为低权重信号，不能直接处罚。

成熟系统会结合长期历史和多个信号。Steam 的 Trust Factor 使用过去游戏/平台经验并在匹配前提示可能的低信任影响，同时不公开全部因素以降低针对性操纵。这可以借鉴为“匹配与风险提示”，但 TokenGame 不能假装已经拥有同等规模的数据和反滥用能力。

来源：

- Steam CS2 Trust Factor Matchmaking：https://help.steampowered.com/en/faqs/view/00EF-D679-C76A-C185

建议首版信用表现使用 New / Established / Caution / Restricted 等分级，而不是显示精确 0–100 分。任何降级都要记录 reason_code、证据、操作者/自动规则、申诉状态和恢复条件。

用户要求赛中检测到违规升级后踢出并重扣信用。该要求可以只绑定 `confirmed higher-than-ceiling` 协议事件：玩家从合规状态切到超出牌桌上限，且复核条件成立。入桌前选错队列只拒绝；`UNAVAILABLE`、`STALE`、网络/宿主瞬时失败或单一矛盾信号只暂停 AI 并复检，不能重罚。否则信用体系会把基础设施故障误判为作弊，并可被断线攻击或故障注入操纵。

即使触发重罚，事件也只证明 TokenGame 当时可见的结构化信号违反桌规，不证明真实上游模型；处罚记录仍需 reason_code、幂等事件 ID、证据摘要、恢复/申诉路径。

用户已经选择“可恢复的累进重罚”，而不是固定罚分或一次永久封禁。建议把它落实为只影响 honor_history/公平完整性维度的状态机：首次 confirmed higher-than-ceiling 造成显著降级并进入临时 Restricted；同一滚动窗口内后续 confirmed 事件按 strike 序号单调增加限制强度和期限；窗口外如何衰减以及通过时间、干净牌局或两者组合恢复，继续作为独立产品决策。举报、UNAVAILABLE、STALE、基础设施故障和单一矛盾信号不能增加 strike。

用户随后选择“两阶段恢复”，并进一步指定观察期在自由场完成、按实际操作次数累计：Restricted 阶段执行不可绕过的公平场冷却，但继续允许开放能力桌且不累计恢复进度；冷却到期仅转为 Caution。Caution 仍不能进入公平场，只能在普通 OPEN_CAPABILITY 自由场累计 qualifying action credits；达到版本化门槛后恢复的是公平场申请资格，而不是一个自动 MATCH receipt。重新入公平场仍须确认公告并通过当时的完整检测。成功申诉是纠错事件，可直接撤销错误后果，不需要走自然恢复。

自由场没有 model/effort ceiling，因此 action credit 只能证明玩家按要求实际参与了恢复活动，不能证明其模型配置合规。自由场使用高级模型本身完全合法，不能形成新的 higher-than-ceiling strike。为避免反复最小加注对刷，每个 hand_id + betting_street 最多一份 credit；fold 必须与 check/call/bet/raise/all-in 同等计入，避免恢复机制扭曲正确弃牌策略。盲注、超时/自动动作、聊天、拒绝/重复请求不计，候选只在 HAND_SETTLED 后按 action_id 幂等入账。冷却时间、required_action_credits 和滚动窗口都必须作为 policy_version 参数，而非散落在客户端的常数。

用户选择只计算玩家本人明确提交的 MANUAL 动作。ADVISOR 可以建议，但建议事件本身不计；玩家通过独立确认动作入口提交后，最终动作才可标记 MANUAL。AUTOPILOT 自主动作即使合法也不计恢复进度，以免玩家挂机完成“实际操作”观察期。来源必须由协调器根据用户输入链、提案与确认关系判定，客户端自报 manual=true 不可信，后续切换模式也不能追溯改写 control_origin。

用户选择只有官方公共匹配自由场能产生恢复 credit。未来正式系统需要由匹配服务签发不可由房主/客户端修改的 `match_origin=PUBLIC_OPEN_POOL` 与 `recovery_eligible=true` 凭证，并绑定 table_id、match_id、ruleset_hash 和资格策略版本；私人邀请、好友/自建/自托管、直接加入、开发/演示、机器人测试和离线牌桌不计。资格无法验证时应让自由场牌局继续但不计恢复分，不能为了信用旁路破坏扑克可用性。

当前本地原型不存在可信公共匹配与远程身份，因而只能通过显式 LOCAL_SIMULATION fixture 验证 eligible/ineligible、幂等和 UI 投影；这些本地 credit 不得导入未来正式信用。即便未来只允许公共匹配，仍需处理排队狙击、同一对手重复匹配和多账号合谋，不能把“公共池”误当成已经解决反刷。

用户在知悉上述风险后选择不限制重复对手：有效 PUBLIC_OPEN_POOL 中的合格动作不因 opponent_id 或桌组重复而封顶、衰减，也不要求最低不同对手数。这优先保护早期小规模队列的可恢复性，但固定小团体可通过排队重逢对刷，属于明确接受的残余风险。实现仍应在私有审计中保留最小化 match/opponent 引用用于未来评估；当前不能仅因重复匹配自动扣 credit、认定合谋或公开风险标签。未来改变必须通过新 policy_version 前向生效，不能追溯重算旧 credit。

用户选择当前 MVP 只使用加速的 LOCAL_SIMULATION 策略，不预先拍定生产处罚数字。本地 fixture 可以用 60 秒冷却、5 个 MANUAL credits 等短参数和可注入时钟快速跑完整状态机；未来 PRODUCTION 在没有可信服务签发的完整 policy_version 时必须显示 POLICY_UNCONFIGURED 并保持长期处罚/恢复禁用，绝不能回退到测试 fixture。当前手的 EJECT_PENDING 与移出是独立牌局规则，仍照常执行。两种模式必须使用不同 namespace/存储标记，测试记录不可迁移为正式信用。

用户选择信用信息“粗粒度公开、细节私有”。公共/对手投影只展示 New / Established / Caution / Restricted 徽章、公平场 ELIGIBLE / RECOVERY_ONLY / BLOCKED 准入状态以及当前是本地模拟还是真实平台信用；精确分数、strike 数、处罚事件与原因历史、证据、剩余冷却、action credit 进度和申诉材料仅对本人及未来授权治理角色开放。当前手的“完整性违规 · 待移出”仍是必须公开的比赛事实，但它不能成为读取其他历史记录的入口。

该边界比公开精确总分更不易诱发刷分、围攻和针对阈值的规避，也比完全隐藏更能解释匹配资格。实现时必须通过服务端/协调器投影白名单隔离，而不能只在前端隐藏字段；否则浏览器网络响应、回放或导出仍会泄露细节。

处罚策略必须版本化。每条记录至少保存 policy_version、penalty_event_id、reason_code、净化证据摘要、strike_index、处罚前后等级、限制条件和申诉/恢复状态。同一事件重放不得重复加罚，未来策略变更不得追溯重算历史；成功申诉通过新的反向事件撤销有效后果，但保留原记录和纠错轨迹。由于检测明确“不保证”，单次自动事件不应产生永久公平场封禁。

用户选择不回滚当前手：confirmed higher-than-ceiling 后席位立即进入 EJECT_PENDING，停止 AI、聊天、私聊与玩家动作；未 all-in 时在下一个合法行动点由权威服务自动 fold，已投入筹码留在底池；已经 all-in 或不再有行动点时按标准扑克规则结算；HAND_SETTLED 后移出并执行一次幂等处罚。这样避免玩家在即将输牌时故意触发检测来撤销整手，也避免非标准没收/退款改变其他玩家权益。

EJECT_PENDING 必须跨刷新、断线和事件重放持久化；迟到模型回答不得公开、执行或返还已耗额度。违规原因状态可以公开以解释强制弃牌，但原始配置、provider、中转和私密内容继续保密。

## 反滥用要求

- 举报限频；同一举报人对同一牌局/对象的重复报告合并。
- 同局互相报复、固定小团体互刷、短期新账号集中举报需要降权。
- 未经复核的举报数量不公开，避免形成围攻标签。
- 举报人恶意提交虚假证据可影响其 feedback 权重，但不能仅因多次未成立就自动处罚。
- 信用处罚需要申诉与可恢复路径；模型配置怀疑在没有可验证证据时不能形成永久处罚。
- 累进处罚只读取已确认且未被撤销的公平完整性 strike，不读取玩家举报数量或其他信用维度；精确扣分、限制期限和恢复门槛应在有账户规模与遥测后通过版本化策略配置，而不是在原型阶段硬编码。
- 全局信用必须依赖远程账户、持久身份、反多账号、服务端证据留存和人工/规则复核；当前本地四人原型不具备这些基础。

## 建议的阶段边界

当前聊天内核/MVP 可以实现或预留：

- table_type = OPEN_CAPABILITY | HONOR_MATCHED；
- HONOR_MATCHED 的 PUBLIC_STANDARD_POOL | PRIVATE_CUSTOM_ROOM 入口类型、版本化目标目录与邀请合同；
- 目标 model/effort、结构化 detection receipt/状态机、全桌安全上限、私有能力配置与不可变 ruleset_hash；
- 对手/公共投影的能力字段净化合同；
- 入桌前风险公告、玩家确认与 detection receipt 事件；
- 桌面/回放持续的“检测不保证”标识和当前检测状态；
- report envelope、本地证据导出、处罚事件、版本化策略归约与可重置的本地模拟；界面和导出必须标记为 LOCAL_SIMULATION/非平台信用，不产生可信全局处罚。
- 当前手 EJECT_PENDING、强制弃牌和 HAND_SETTLED 后移出仍由本桌权威状态机真实执行；长期等级和 Restricted 状态的本地模拟写入失败不能回滚牌局。

未来远程账户阶段再实现：

- 服务端举报队列、复核工作台和申诉；
- 分维度信用与匹配提示；
- 反 Sybil、多账号和举报团伙识别；
- 处罚、恢复和审计。

用户已选择这一阶段边界。本地模拟的价值是提前验证事件幂等、策略版本、strike 升级、恢复/申诉反向事件和 UI 状态，而不是制造可以通过删文件重置的“伪信用”。未来服务端可以复用事件合同和归约逻辑，但未经可信服务签发的本机历史不得直接导入为正式处罚。

## 当前建议

保留开放能力桌和“公平场 · 检测不保证”。公平场通过 App Server 结构化信号做入桌与运行中筛选，用来提高普通“高级模型炸鱼”的成本，但不宣传真实上游模型已被证明；玩家训练出的档案、记忆、工具和模块仍可不同且默认对对手隐藏。举报与信用可作为路线图能力；当前原型只应预留可审计的数据合同，不能把检测 receipt 或尚未复核的举报升级成永久作弊定罪。
