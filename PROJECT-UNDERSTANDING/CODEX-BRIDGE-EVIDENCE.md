# Codex 桥接证据、推导与反证条件（R4）

## 已核实事实

- 本机为 `codex-cli 0.145.0`；稳定能力清单中存在 plugins、hooks、apps，`enable_mcp_apps` 在本机仍显示为未启用的开发中能力。
- [Codex Hook 文档](https://learn.chatgpt.com/docs/hooks)说明 `UserPromptSubmit` 提供 `turn_id` 与即将提交的 `prompt`，`Stop` 提供 `turn_id` 与 `last_assistant_message`；通用输入还包含会话、工作目录、事件和模型标识。文档同时把 transcript 格式标为不稳定接口。
- 同一 Hook 文档说明同步 Hook 会在继续前等待；异步 Hook 可能乱序、会在会话结束时取消，也不能阻止或控制当前流程。因此核心公开时序应先验证同步路径，异步路径不适合承担“提示必须先公开”的合同。
- [插件构建文档](https://developers.openai.com/plugins/build/plugins)和 [MCP 服务打包文档](https://developers.openai.com/plugins/build/mcp-server)支持插件捆绑 Skill、Hook 与 `.mcp.json` 声明的本地 stdio MCP 服务；Hook 可使用 `PLUGIN_ROOT` 定位资源，并使用可写的 `PLUGIN_DATA` 保存私有状态。文档没有保证旧式捆绑 MCP 进程获得同一个 `PLUGIN_DATA`。
- [插件使用说明](https://learn.chatgpt.com/docs/plugins)要求安装新插件后启动新聊天或新 CLI 会话使用其能力。这支持“安装后进入专用游戏任务”，不支持承诺旧会话无条件热激活。
- [开发命令说明](https://learn.chatgpt.com/docs/developer-commands)公开了内建斜杠命令和 `$<skill-name>` 调用方式，没有给出插件注册任意 `/tokengame` 斜杠命令的稳定合同。
- [远程 MCP 鉴权文档](https://developers.openai.com/plugins/build/auth)说明远程认证采用 OAuth 2.1，并由宿主把访问令牌附着到 MCP 请求。
- [MCP UI 指南](https://developers.openai.com/plugins/build/chatgpt-ui)把组件描述为运行在 ChatGPT iframe 中，并要求工具在没有 UI 时也能工作。它证明 MCP Apps UI 标准存在，不证明当前 Codex 桌面必然渲染 TokenGame 牌桌。
- Hook 输入没有公开的推理强度字段。用户选择的当前会话模型和推理强度仍会影响本回合生成，但 TokenGame 不能从 Hook 读取或证明强度。

## 真实宿主直接证据

2026-08-26 在 `codex-cli 0.145.0` 的无秘密专用任务中，通过仓库本地 marketplace 安装并执行了 TokenGame 插件，随后完整卸载。逐项原始结果与清理核对见 `docs/HOST-PROBE-CHECKLIST.md`。

- `$tokengame public 请只回复：HOST_PROBE_OK` 的 prompt 事件先进入权威流，最终消息 `HOST_PROBE_OK` 后进入同一请求的 answer 事件；`PreToolUse` 在回答 pending 期间拒绝无关本地工具。
- 普通 prompt/Stop 对桥和权威事件均为零流量；同一窗口第二次公开请求和关窗后的公开请求在模型生成前被拒绝。
- 真宿主发现并调用捆绑 MCP 状态工具；桥故障后，真宿主又通过 `publish_ai_answer` 把保留的原始回答补交为唯一权威 answer 事件。
- 插件安装不自动信任 Hook。不显式授予一次性信任时，模型正常回答但 Hook、桥与权威流均不动作。
- 真宿主暴露了 Stop 重入会覆盖 pending 原回答的缺陷；`stop_hook_active` 保护修复后，原始长回答保持不变并通过自动化回归。
- Hook 获得 `PLUGIN_ROOT`/`PLUGIN_DATA`，但本次旧式捆绑 MCP 进程没有获得 Hook 的 `PLUGIN_DATA`。因此补交的服务端幂等闭环通过，本地 pending 即时归档仍是非阻塞生命周期缺口。
- 多次 `codex exec` 插件刷新留下本次 MCP 子进程并短暂占用缓存；精确结束本次进程后，插件、marketplace、信任配置、缓存、数据、端口均清理为零。

## 关键推导（不是文档原句）

### Hook 不能被假定继承 MCP OAuth

官方资料只保证宿主把令牌附着在 MCP 请求上。独立 Hook 命令自行发出的 HTTP 请求不等于 MCP 请求，所以不能假定它自动取得同一令牌。这是从两个接口边界作出的架构推导。

因此加入捆绑本地 stdio MCP 桥：桥负责认证状态、远端连接、重连和持久化；Hook 只通过受限本地 IPC 传递已匹配的事件。生产环境究竟采用宿主 OAuth、本地设备码、短期会话票据还是二者组合，必须在后续集成中另行验证。

### 外发过滤不能防止模型复述旧上下文

只让显式提示通过 Hook，能防止普通提示被直接上传，却不能阻止模型在公共回答里提到同一会话以前读过的文件、凭据或私聊。这是语言模型上下文边界带来的产品风险，不是 Hook 过滤 bug。

合理缓解是新建专用 TokenGame 游戏任务、只注入最小结构化牌局事实、把对手文本隔离为不可信数据，并在公共回合待处理时限制非游戏工具。该组合只能形成可测试的风险控制，不能被宣传成形式化零泄漏证明。

### 本地模型标识不是远端防伪证明

Hook 可以观察模型标识，但插件和本地进程由玩家控制，恶意客户端可以伪造事件。故服务端能验证的是会话令牌、事件序号和协议一致性，不能仅凭客户端字段验证“这段话一定由 Codex 官方模型生成”。MVP 的正确标签是“玩家的公开 AI 频道”；平台签名证明是未来外部依赖。

## 修订后的职责边界

### Codex 插件

- 提供 `$tokengame` 或插件提及入口、使用说明和明确的公开提示警告。
- 安装严格范围的同步 Hook；不信任 Hook 配置时不自动启用外发。
- 捆绑本地 stdio MCP 桥，并将私有状态限制在插件数据目录。

### UserPromptSubmit Hook

- 解析精确的 TokenGame 公共请求格式，验证活跃游戏会话和本地待处理状态。
- 普通提示立即放行且不访问桥接进程或网络。
- 对游戏请求调用本地桥，由远端原子占用窗口唯一额度并写入 `PROMPT_PUBLIC`；失败时阻止该游戏请求继续生成。
- 只把服务端签发的请求 ID、截止时间和经清理的最小上下文注入本回合。

### Stop Hook

- 只处理具有同一会话、回合、请求和窗口绑定的最终消息。
- 不读取 transcript，不用“最近一条消息”猜配对，没有记录就丢弃。
- 把候选回答交给桥，由服务端按自己的时间和状态决定是否进入 `ANSWER_PUBLIC`。
- 若实测无法可靠满足合同，退回显式 `publish_ai_answer` MCP 工具，不能偷偷降低时序要求。

### 本地 stdio MCP 桥

- 保存最小会话绑定、短期凭据、请求状态和幂等信息；不保存整个 Codex transcript。
- 统一处理远端认证、连接、超时、重连和错误分类。
- 为 Hook 提供窄 IPC，而不是开放任意远程代理。

### 远程权威服务

- 用服务端时钟、行动窗口、请求 ID、单调事件序号和幂等键裁决请求。
- `PROMPT_PUBLIC` 一经提交不可因客户端断线撤销；行动结束后的回答被拒绝且不进入实时流。
- 牌局事实、合法行动、底牌隔离与结算始终由服务端维护。
- MCP/本地控制面与 WebSocket 或 SSE 实时数据面可分离，但共享同一个权威领域事件层。

### 独立 Web 牌桌

- 展示官方事实、AI 公共事件、剩余时间和迟到状态；语言声明与官方事实视觉分栏。
- 由真人提交官方行动，安全渲染所有公共文本并限制载荷长度。
- 断线后按服务端序号恢复，不依赖浏览器本地状态猜测牌局。

## 候选路线复核

### 纯 Skill

仍然不够。它能使用当前模型，却没有权威多人状态、认证、广播、幂等和持续牌桌视图。

### Hook 直接访问远端

被替代。它看似组件更少，但 MCP OAuth 不自动等同于 Hook HTTP 鉴权，且重连、短期凭据和事件恢复会散落在多个命令进程中。

### 插件、同步 Hook、本地桥、远端服务和 Web 视图

当前推荐，并已通过 Codex 真宿主聚焦探针。它保留当前会话生成和 Codex 原生入口，同时把认证、实时性、权威状态和 UI 分到可单独验证的层。宿主探针只证明该分层的最小闭环，不证明远端生产质量。

### 独立 Codex App Server 客户端

以后可重新评估。它可更直接控制 Thread、模型和 effort，但会把“安装一个游戏插件”扩大为“另做一个 Codex 客户端”，不是当前 MVP 的最短风险消除路径。

### 独立 OpenAI API 助手

继续拒绝。它增加第二套调用配置，回答也不再是用户当前 Codex 会话的实际输出。

## 结论

更高强度复审没有否定项目可行性，也没有发现需要修改已确认产品语义的理由。它确实发现了旧架构的一处实质缺口：Hook 与远端之间缺少明确的本地桥接和鉴权所有者；同时补出了上下文泄露与来源证明两项此前表达不足的风险。

修订后的架构和真实宿主最小闭环获得 `APPROVE_WITH_NOTES`。现在可以声称“TokenGame 的 Codex 插件宿主桥接路径已通过本地可逆探针”，并把 TG-L3/TG-L4 关闭；不能省略限定词写成“完整 Codex 产品集成已经可用”，更不能推导为多人 MVP、生产认证、桌面内嵌 UI或公开发布就绪。
