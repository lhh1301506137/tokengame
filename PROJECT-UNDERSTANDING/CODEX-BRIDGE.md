# TokenGame Codex 桥接宿主结论（R4）

## 这次在理解什么

- **主题：** TokenGame Codex 会话桥接、隐私边界与公开事件协议

- **项目位置：** 当前路线为 TG-L0-PRODUCT → TG-L1-LIVE-TABLE → TG-L2-PLAYABLE-TABLE。首个未验证点是 TG-L3-MULTIPLAYER-VERTICAL-SLICE，状态为未验证。下一开发叶是 TG-L3-MULTIPLAYER-VERTICAL-SLICE。TG-L3-CODEX-BRIDGE-SPIKE 不在当前路线，是已经关闭的前置主题。

- **承接的理解：** 当前 MVP 已确认以 Codex 为入口，只公开 TokenGame 专用游戏提示及其对应回答，官方牌局行动仍由真人提交；普通提示、文件、历史和凭据必须保持私密。

- **负责与下游输出：** 本轮用真实 Codex 插件宿主验证 Hook、本地桥、MCP、权威事件服务和独立 Web 牌桌的最小闭环，并给出能否转入多人牌桌开发的证据结论。

- **本轮包含：** 本地 marketplace 安装、Hook 信任、同步提示预公开、Stop 回答配对、普通内容零桥流量、重复与关窗拒绝、PreToolUse、MCP 调用、桥故障补交、卸载清理和自动化回归。

- **本轮不包含：** 完整扑克引擎、生产 OAuth、真实多人部署、账号与内容治理、不可伪造来源证明、Codex 桌面原生牌桌 UI、真实筹码、公开发布和最终产品验收。

## 结论

Codex 插件宿主聚焦探针通过，结果为 `pass_with_notes`。当前会话模型能在公开提示已由权威服务接受后生成回答；最终消息能与同一请求配对公开；普通 Codex 提示和普通 Stop 不触发 TokenGame 桥；故障回答可通过捆绑 MCP 显式补交；插件安装和信任也能完整撤销。

这足以关闭桥接与宿主探针节点，路线转向第一手完整多人牌局。它不等于完整 Codex 产品集成或桌面内嵌牌桌已经实现。

R4 是从当前宿主证据与当前 Plan Tree 重新冻结的理解投影；它不把 R3 的校验调用错误当成产品失败，也不沿用未通过的投影绑定状态。

## 真宿主改变了什么

本地模拟没有发现、真宿主实际暴露了一个 Stop 重入缺陷：桥不可达时，Codex 会生成一条说明失败的后续文本并再次触发 Stop，旧实现会用说明覆盖原始回答。现在 `stop_hook_active` 时直接退出，原始回答保留，并有自动化和真宿主回归证据。

同时确认了两个生命周期边界：安装 Hook 默认不自动受信任；Hook 的 `PLUGIN_DATA` 在本次运行中没有自动传给旧式捆绑 MCP。因此显式补交能完成服务端权威事件闭环，但补交后的本地 pending 不能立即归档。该缺口和 MCP 子进程正常回收需要在产品化时解决。

## 仍然成立的架构

`显式 TokenGame 请求 → 同步 Hook → 本地桥 → 权威事件/牌局服务 → 独立 Web 牌桌`

Hook 只识别严格范围的公开请求；桥拥有连接、认证和幂等职责；服务端以窗口、请求 ID、服务端时钟和单调事件序号裁决；Web 牌桌观察同一权威事件并承载真人官方行动。模型标识可以作为体验元数据，但本地可修改插件不能提供不可伪造的 Codex 来源证明。

## 下一步

按照既定建议先初始化 Trellis，再定义固定测试桌的一手完整多人牌局纵向切片。首个切片应优先证明服务端权威状态机、合法行动、回合推进、胜负结算和可观察验收，不应先投入 Codex 桌面内嵌 UI 或生产发布。
