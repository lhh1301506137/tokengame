## 两次显式开启

第一层是让本地beta拥有一个固定发送目标。Codex当前任务的首选入口是：

```powershell
npm run codex:play -- "<当前 Codex 项目根绝对路径>"
```

它只读取、校验并小写化`CODEX_THREAD_ID`，不读取、比较或回退`CODEX_SESSION_ID`；先只读验证唯一绝对项目、
仓库包含关系、thread与可信可执行文件，全部通过后才原子配置。首次若受管配置发生变化，命令只输出去敏
重启提示并停止，不启动beta；由真人重启目标Codex任务后必须重跑同一命令。配置相同不等于当前宿主已
加载工具，仍须以重启后的实际工具发现为准。入口不覆盖模型或推理，不自动开通知窗或枚举其他任务。
受管块的`cwd`是canonical仓库绝对目录，仅用于本机stdio启动；它不是令牌或席位凭据，也不会出现在稳定
CLI/UI输出中。仓库跟踪的`.codex/config.toml`仅为可移植模板，其中`cwd = "."`不能替代入口为真实上层
Codex项目生成的受管块，也不能作为运行态证据。真人生成在上层Codex项目中的`.codex/config.toml`会包含
本机目录布局，不要分享或提交Git；仓库随源码跟踪的可移植模板不在此列。

直接`npm run beta`保留为高级手工兼容。它默认没有发送器，也不会启动Codex；需要managed通知时，由本机
操作者在**当前启动进程的环境**明确设置以下四项。该手工路径不从PATH猜可执行文件：

| 变量 | 内容 |
| --- | --- |
| `TOKENGAME_CODEX_WAKE` | 精确的 `1`；未设、空串或 `0` 为关闭，其他值报配置错误 |
| `TOKENGAME_CODEX_EXECUTABLE` | 本机 `codex.exe` 的绝对路径；手工beta不从PATH猜测 |
| `TOKENGAME_CODEX_CWD` | 该游戏任务的明确工作目录，不是普通开发任务 |
| `TOKENGAME_CODEX_THREAD` | 已有专用游戏任务 UUID；不创建任务，不覆盖模型或推理强度 |

两种方式都只使启动行显示`managed_wake: available`并让服务端报告`target_configured: true`，不会开始轮询或
通知。`codex:play`在Windows无显式可执行文件时有自己受限的可信PATH解析；这不改变手工beta必须给绝对路径
的规则；非Windows使用`codex:play`也必须显式提供可执行文件。`proactive_wake_verified`仍为`false`。

beta启动后先结束目标Codex任务的当前回复，让它保持空闲，再在Web牌桌开启通知窗口。不要让启动回合持续
看守牌桌，也不要一边让该任务做开发工作一边期待它并发处理牌桌通知；通知传输可能已经接收，但新模型
回合要等当前回复结束，窗口可能先到限。

第二步仍需本人在当前牌桌完成公开范围确认、模型连接授权，并为一个有界窗口发送真人控制请求。可以使用下面的牌桌表单；工具清单没有这些控制命令，模型不能代本人开启窗口。模型原任务的 MCP 必须已接到同一席，否则收到通知后会因不匹配而被拒绝。

## 在牌桌上操作

1. 展开“连接我的会话 AI”。先完成原有本席连接，并保持座位 AI 开启；仅绑定不会自动发送通知。
2. 固定sender模式显示“发送器已固定当前游戏任务，UUID不向页面公开”，同时提醒目标任务先结束当前回复并保持空闲；UUID区域真实隐藏且disabled，页面不会提交`thread_id`，也不能改换目标。只有旧/自定义queue兼容模式才显示可编辑UUID输入并按旧合同提交。两种模式都选择最多通知次数和最长持续秒数；页面显示服务实际限制，默认表单为1次、60秒，服务更严格时向下取限。每窗确认同时声明目标任务当前可接收新回合。
3. 核对后勾选本次窗口确认，再点击“开启有限通知窗口”。每个新窗口都要重新确认；改变参数会取消勾选。`target_configured`不是严格布尔、未配置发送器、旧兼容模式缺合法UUID、未绑定、AI OFF、公开范围未确认或能力数据不合法时均失败关闭。
4. 可随时点击“停止后续通知”。想禁止已经在途的 AI 后续公开，则关闭本席 AI 或撤销 AI 连接。按钮不会撤回已被宿主接收的通知，也不会删除已经公开的发言。

状态中的“尝试 / 已接收 / 权威已结清”是三种不同事实。已接收不是模型已完成；已结清包含公开、silent 或合法丢弃，不是公开回复数。时长和上限由服务端报告，页面倒计时不决定停止。清理未确认时不能声称干净停止，原生任务的整轮状态仍是 `unknown`。

开启结果不确定时，不会自动再投。页面保留本次`request_id`和原参数，而不是目标任务UUID；只能显式“核对并重试原请求”，也可以表达停止意图。一旦选择停止，后续重试只核对或停止原请求，不会再次开启。新请求没有同键回执时不显示上一窗口的原因、计数或清理结果。刷新页面不会自动重投未确认请求；页面既有轮询只读本席当前窗口，不另开调度循环。

可选通知模块加载缓慢或失败时，原牌桌会话仍能恢复，真人可继续操作。正在处理的 OFF、换绑或撤销会阻断通知控件；模块迟到加载以及多个操作完成顺序不同，都不能提前解除这一阻断。

## 本机真人控制接口

全部是相同源的 `POST` JSON，仅供受信本地客户端调用。`session_token` 按现有浏览器行为保存在内存和本标签页的 `sessionStorage`（被浏览器禁止时退回内存），不写 `localStorage`、URL 或公开日志，不可粘贴给模型；权威席位凭据仍只由协调器持有。这是既有恢复机制，不是 B16 新增的持久存储。

- `/api/model/wake/start`：共同字段为`session_token`、`acknowledged: true`、新UUID `request_id`，可选`max_notifications`和`max_duration_ms`。固定目标的官方页面与推荐客户端省略`thread_id`，由服务端安全选择唯一预配置任务；低层兼容请求若显式提供，则仅精确匹配的合法ID可接受，畸形ID返回`invalid_field`，合法外来ID返回`wake_thread_not_authorized`，且成功或错误响应均不回显ID。旧/自定义queue兼容模式仍必须提供合法`thread_id`。默认beta服务上限是4次和600000毫秒，允许服务收紧，实际取值看`model_wake.limits`；这是上限，不保证产生同等数量AI回答，页面默认值与API省略参数时的默认上限不同。
- `/api/model/wake/status`：`session_token`，可选 `request_id`；不传时查看本席当前或最后窗口。
- `/api/model/wake/stop`：同 status，等待该窗口自己的发送器结束收尾；重复调用不重复发送或撤回旧牌局动作。

响应为`{ ok: true, wake: ... }`。轮询和start/status/stop的成功或错误响应都不返回`thread_id`；固定目标只以`target_configured`布尔表达，不回显真实ID。状态包含`state/reason`、尝试/接收/已观察resolve计数、时间上限、清理是否确认。`ai.start`或`ai.resolve`失败时可另外出现`failure_code`：它只接受固定语法的稳定业务码，用来区分待办失效、claim换代等原因；自由文本、`details`、异常正文和上游响应一律不进入窗口或页面。没有合法码时该字段省略，不能从通用`wake_start_failed`/`wake_resolve_failed`倒推具体原因。不返回聊天正文、底牌、模型令牌、恢复凭据、进程路径或隐藏推理。`native_turn_state: unknown`是有意保留：牌桌收到resolve，并不证明宿主已结束整轮生成。

既有`/api/view`另外返回`model_wake: { enabled, target_configured, limits: { max_notifications, max_duration_ms }, window }`。`window`只投影当前查看者的有效本席绑定；未绑定为`null`，不暴露窗口目标任务、其他席位窗口或后台配置。`enabled`只表示本机发送器可用，`target_configured`只表示它能安全选择固定目标；两者都不是原生能力证明。

重复 start 的同键同参数只回放当前/终止状态；同键改参数报冲突，旧停止键不复活。要开另一个窗口须本人明确提供新键。绑定、请求历史、已通知 intent 及任务配对都有上限，满额报错而不逐出旧记录来制造“新”请求。

## 连续运行规则

1. 在没有待确认通知时，协调器通过本席已有权限领取权威意图。空待办只等待数据，不调用模型。
2. 权威决定来源、合并、冷却、每手额度及租约。通知只携带编号和固定控制说明，不把不可信玩家正文拼入控制指令。managed固定说明要求首项工具立即调用`ai.start`，但宿主是否实际遵循只能由可见工具回执证明；任务`items=[]`时必须记为unknown。
3. queue 进程接受后，窗口停在等待结果。直到同一 intent 对应 turn 的实际 `ai.resolve` 成功，才允许下一条通知；正常公开、silent、合法丢弃都要由实际回执证明，不从“没看到气泡”猜测。
4. 多个事件在模型忙时仍由权威合并为一个最新上下文，不在协调器另造聊天 FIFO。AI 回复本身不制造新的模型互聊循环。
5. 达到通知/时间上限、AI OFF、离桌、撤权、协议异常、超时或未知接收时停止后续通知，不重试同一个 intent。

## 停止与隔离的真实边界

- 停止窗口只停止后续领取/发送。已被 Codex 接收的消息可能继续运行，不能承诺撤回；要禁止后续公开，使用已有的 AI OFF 或撤销模型连接，其权威围栏会拒绝迟到结果。
- 同一协调器运行期间，一个原生任务只能配对一个席位。即使上一轮已经结束，也不能把 A 的任务改给 B，因为上下文可能仍有 A 的未公开牌面。
- 同席只有在旧窗口没有待确认通知、或已记录精确 resolve，且发送器清理已经确认后，才可显式重开。这一保护覆盖该席位已撤销的绑定：清理未知/失败返回 `wake_cleanup_failed`，结果未确认返回 `wake_result_pending`；换绑定、请求键、任务编号或重建管理器都不能跳过旧事实。当前 beta 的发送器仍固定到启动时配置的任务，没有运行中换目标入口。撤权时旧通知结果尚未确认会保守阻止自动恢复，本批不提供无缝重连，也不自动重投已预留的 intent。
- 若取消/到期发生在调用发送器之前，状态如实记录零次尝试、零次接收和无需清理发送资源，并清除不存在的待确认通知；已预留 intent 的去重记录仍保留，不撤回权威 claim，也不自动重试。真人可另开窗口，但续领同一已预留 intent 仍会被拒绝。进入发送器后的缺失回执仍保持未知。
- 发送器只管理自己创建的短命 queue 进程，不创建常驻 MCP、不读取/复制/删除私有连接文件、不接管已有进程、不重启桌面宿主。
- 当前仍仅监听本机回环。不能把这个地址直接发给异地朋友，也不代表安装向导、实时性或四人验收已经完成。
