## 这次在选择什么

两个方案都遵守已经确认的宿主中立 L0，也都允许 Codex 与 Claude 适配器分阶段交付。区别不在页面长什么样，而在“宿主入口”是否属于同一个产品能力域：

- **方案 1：共享宿主中立入口。** 只有一个 `TG-L1-HOST-ENTRY`，Codex、Claude 是其下不同适配；旧 Codex 入口合同转为历史。共同身份、房间归属和恢复含义天然只有一份。
- **方案 2：并列宿主入口。** 保留既有 `TG-L1-CODEX-ENTRY`，新增兄弟 `TG-L1-CLAUDE-ENTRY`；每个宿主拥有独立 L1 入口章程，再用共同约束接到同一核心。

**Primary 建议方案 1。** 宿主差异主要来自安装、输入和 UI 能力，放在同一入口域的下层适配更合适；方案 2 会让每新增一个宿主就新增一套 L1 语义与维护边界，更容易逐渐形成两套产品。只有当你认为“Codex 入口体验”和“Claude 入口体验”本身应当长期作为两个并列的一级产品能力分别演进时，方案 2 才更合适。

## 方案 1：共享宿主中立入口（推荐）

**完整目标**：让用户能够从任一受支持的 AI 工作宿主自然进入同一个 TokenGame，把当前游戏会话实际使用的 AI 与一个宿主中立的玩家会话连接起来，并进入或恢复后续牌桌，而不要求另配一套模型 API。

**在 L0 中的责任**：承担产品主链中统一入口与会话承接责任：各宿主适配器分别处理本宿主可靠的安装、授权和交互形态，共享入口则向后续牌桌交付含义一致的玩家身份、游戏会话和 AI 能力边界；它不决定牌局规则或公开交流规则。

**包括**：

- 允许 Codex、Claude 及以后受支持宿主通过各自可靠的交互形态接入同一个 TokenGame，适配器可以分阶段交付。
- 在用户明确允许后安装或启用 TokenGame，并把当前游戏会话与玩家的参赛身份显式绑定。
- 使用该游戏会话实际采用的模型、推理配置和可用工具作为 AI 能力来源，不要求平台验证模型提供商身份，也不要求用户另填模型 API。
- 清楚显示当前游戏、AI 参赛、房间连接和恢复状态，并为中断后的继续游戏提供入口。
- 为所有宿主使用同一套玩家身份、房间归属和恢复含义，使后来加入的宿主不需要重做牌桌核心。

**明确不包括**：

- 不要求各宿主使用相同的输入框、控件、页面布局或自动化接口。
- 不承担德州扑克状态裁决、隐藏信息保护，也不决定哪些赛时内容公开。
- 不为每个宿主建立互不兼容的账户、房间命名空间或独立牌局核心。
- 当前 MVP 不要求两个宿主适配器同时完成，也不承诺跨设备同步、公开匹配或应用商店分发。

**完成后用户得到什么**：用户无论从哪个已经受支持的宿主进入，都能用少量明确操作启用同一个 TokenGame，带上当前游戏会话真实使用的 AI，看到自己是否已连接或可恢复牌桌，而不必重新配置另一套 AI 客户端。

**上下游关系**：

- 上游依赖用户对安装、联网和会话能力的明确授权，以及各宿主能够可靠提供的接入能力。
- 向可信实时牌局能力提供宿主中立的玩家会话、加入或恢复请求和明确的身份归属。
- 向公开人机博弈能力提供经过边界控制的当前会话 AI 入口；宿主特有输入形态由后续章程适配。

**理想最终形态**：形成一条稳定的 TokenGame 宿主入口主链：玩家可以选择受支持的 AI 工作宿主而不更换游戏身份或进入另一套牌局核心，各宿主的进入体验保持自然，但共享状态、隐私说明和恢复结果保持一致。

**当前 MVP 边界**：先让至少一个宿主适配器完成显式安装或启用、绑定一个当前游戏会话、开启或关闭 AI 助手、连接或恢复一个临时私人德州牌桌；另一个宿主可以稍后接入，但玩家身份、房间归属和恢复含义不得写死为首个宿主专属。

**典型成功场景**：玩家 A 在 Codex 中启用 TokenGame，玩家 B 在 Claude 中通过该宿主可靠入口启用同一游戏；两人各自绑定当前游戏会话并加入同一个私人房。即使首个 MVP 只先交付 Codex 入口，后来增加 Claude 时也沿用同一玩家与房间含义，不重做牌桌核心。

**看似完成但语义错误的情况**：分别制作 Codex TokenGame 和 Claude TokenGame，两边各有自己的玩家身份、房间和恢复规则；它们都能打开牌桌，却无法自然进入同一场比赛，最终形成两套名称相同但互不兼容的产品。

**选择该方案会怎样**：建立 `TG-L1-HOST-ENTRY` 后继合同并替代旧 `TG-L1-CODEX-ENTRY` 作为当前入口域；旧合同继续保留为历史。Codex 与 Claude 的具体入口差异留给后续 L2 章程和 AI 自主实现层处理。

## 方案 2：Codex 与 Claude 并列入口

**完整目标**：在保留既有 Codex 入口能力域的同时，为 Claude 用户建立一个并列的 TokenGame 入口与会话承接能力域，使 Claude 的当前游戏会话 AI 能够进入或恢复同一套权威牌桌，而不要求另配模型 API。

**在 L0 中的责任**：作为既有 Codex 入口的兄弟 L1，独立承担 Claude 宿主中的安装、授权、会话绑定、状态说明和恢复体验；Codex 与 Claude 两个入口可以分别演进，但都必须把玩家交给同一牌桌与公开博弈核心，不能各自定义比赛事实。

**包括**：

- 通过 Claude 实际可靠的 Chat、Cowork、连接器或内嵌交互形态启用 TokenGame，具体形态由宿主证据决定。
- 在用户明确允许后绑定当前 Claude 游戏会话及其实际采用的模型、推理配置和可用工具。
- 显示 Claude 侧的游戏、AI 参赛、房间连接和恢复状态，并支持中断后的继续入口。
- 与既有 Codex 入口共享牌桌能够识别的玩家身份、房间归属和恢复结果。
- 允许 Claude 入口和 Codex 入口采用不同的用户可见进入流程，只要共享核心功能不被削弱。

**明确不包括**：

- 不修改或替代已经存在的 Codex 入口章程，而是新增一个并列宿主能力域。
- 不承诺 Claude 与 Codex 使用相同输入框、自动化接口或页面布局。
- 不让 Claude 入口拥有牌堆、对手底牌、下注裁决或公开交流规则的控制权。
- 当前 MVP 不要求两个入口同时完成，也不承诺跨设备同步、公开匹配或应用商店分发。

**完成后用户得到什么**：Claude 用户能够通过符合 Claude 使用习惯的明确入口带着当前会话 AI 进入 TokenGame，Codex 用户继续使用既有入口；双方最终进入同一权威牌桌，但两个宿主的安装、状态和恢复体验可以分别设计和说明。

**上下游关系**：

- 与既有 TG-L1-CODEX-ENTRY 并列，各自承担一个宿主的入口和会话承接责任。
- 两个宿主入口都向可信实时牌局能力提供可识别的玩家会话、加入或恢复请求。
- 两个宿主入口都向公开人机博弈能力提供受边界控制的当前会话 AI；跨宿主共同不变量仍由共享上层目标和后续章程约束。

**理想最终形态**：Codex 与 Claude 各有一个针对宿主特性充分优化、责任清楚的入口能力域，并通过明确的共同约束接入同一个 TokenGame 核心；增加新宿主时可以新增兄弟入口，而不修改已有宿主体验。

**当前 MVP 边界**：保留现有 Codex 入口合同，并把 Claude 入口作为新增兄弟能力域分阶段实现；首个可玩 MVP 仍可只交付一个宿主，但 Claude 入口一旦交付，就必须使用与 Codex 兼容的玩家身份、房间归属和权威牌桌结果。

**典型成功场景**：Codex 用户继续通过既有项目与会话入口加入私人房；Claude 用户稍后通过 Claude 专用入口绑定当前游戏会话并加入同一房间。两边的安装提示和输入方式不同，但牌桌识别为两个正常玩家，使用同一发牌、行动和结算事实。

**看似完成但语义错误的情况**：给 Claude 制作一个外观不同的入口后，让它使用自己的房间编号、牌局状态或公开规则；这看似尊重宿主差异，实际上把兄弟入口变成了第二套游戏核心，违背已确认的宿主中立 L0。

**选择该方案会怎样**：保留已验证的 `TG-L1-CODEX-ENTRY`，新增并验证 `TG-L1-CLAUDE-ENTRY`。后续每增加一个重要宿主，都可能需要独立的 L1 入口章程及对应维护。
